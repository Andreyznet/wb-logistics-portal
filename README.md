# Маршрут — портал логистов

Версия 0.2.0: настройки бота для администратора и встроенный мониторинг по маршрутам/датам из планов.

## Настройки бота

Вкладка «Настройки бота» видна только администратору. Сервер также проверяет права: логист не может читать настройки/состояние или сохранять их прямым запросом к API.

- **Токен Wildberries**: вставьте access_token из token/merge, с префиксом Bearer или без него. После сохранения поле пустое; отображаются только наличие токена и дата exp, если она есть. Пустое поле при повторном сохранении оставляет старый токен. Для удаления используйте отдельный флажок и выключите бота.
- **Включить бота**: по умолчанию выключен. Изменение применяется после «Сохранить настройки». Выключение прерывает текущий запрос, его запоздавший результат не записывается.
- **Интервал опроса**: по умолчанию 60 секунд, целые значения 10–86400. Между завершением успешного цикла и следующим проходит заданный интервал; параллельные циклы не запускаются.
- Расписание удалено: при включении бот работает непрерывно.
- **Состояние и найденные заявки**: последняя успешная проверка, следующий опрос, ошибки, число кандидатов и последние найденные заявки доступны в той же вкладке. Пока она открыта, состояние обновляется каждые 5 секунд без сброса несохранённого ввода.

Бот выполняется на сервере портала и продолжает работу после закрытия браузера. При перезапуске сервера восстанавливает сохранённые настройки, если ранее был включён. Опрос идёт только при наличии запланированных заявок на текущие/будущие даты. Сначала делается один GET списка WB, затем последовательные GET карточек неназначенных заявок подходящих маршрутов и дат. Дата car_dt сравнивается с датой плана в часовом поясе портала. «Создана» подтверждается карточкой: request_status=created, is_closed=false, supplier_id=null. Неожиданный ответ не считается исчезновением заявки. Повторные неизменившиеся кандидаты не дублируются в журнале найденных.

На 401/403, перенаправлении или HTML вместо JSON бот автоматически выключается с причиной в истории. Введите новый токен и включите его вручную. На временных ошибках/429 опрос откладывается; учитывается Retry-After. Автоматического входа, обновления токена, решения CAPTCHA, принятия заявок и назначения экипажей в WB нет. Telegram в эту версию портала не подключён.

Токен хранится в SQLite зашифрованным AES-256-GCM. Ключ автоматически создаётся в data/bot-secret.key рядом с базой. Токен не возвращается в ответах API и не включается в журнал изменений. Доступ к папке data должен быть ограничен; резервная копия/перенос должны включать **и базу, и bot-secret.key**, иначе сохранённый токен расшифровать не получится. В архив проекта реальные токены, ключ и база не включаются.

При переходе на встроенный бот остановите отдельный wb-monitor-61373, если он тоже опрашивает этот аккаунт, чтобы не запускать два независимых цикла. Сохранение токена в портале не меняет старый auth.json и наоборот.

Для обновления с 0.1.0 остановите портал, замените src, public, test и package.json, затем запустите снова. Сохраните .env и папку data; новые таблицы добавятся автоматически, учётные записи и планы останутся. Docker-образ нужно пересобрать; данные именованного тома сохраняются.

Рабочий локальный/серверный портал для планирования экипажей. Это отдельный проект, существующий `wb-monitor-61373` заменять не нужно. Требуется Node.js 24 или новее. Внешних npm-зависимостей нет.

## Запуск на компьютере

В PowerShell в папке портала:

```powershell
Copy-Item .env.example .env
npm.cmd start
```

Откройте http://127.0.0.1:8787. При первом входе создайте администратора (имя, логин, пароль от 10 символов). Для входа в сам портал пароль WB и Bearer-токен не используются; токен нужен отдельно только для включения мониторинга. Если в `.env` задан SETUP_TOKEN, при создании администратора введите его как код настройки. Без SETUP_TOKEN первоначальная настройка доступна только напрямую с локального компьютера, не через доверенный прокси.

В разделе **Справочники → Импортировать JSON** выберите файл:

```text
G:\Project\wb-monitor-61373\data\directory.json
```

Это файл команды `npm.cmd run directory` из монитора. Поддерживается также исходный ответ GET `suppliers/transport` с тремя массивами внутри `data`. Импортируются только ID, имена, названия, госномера и типы — телефоны и полные профили не сохраняются. Исчезнувшие из новой выгрузки элементы больше нельзя выбирать, но ранее созданные планы остаются в истории.

Для автоматического **первоначального** импорта можно задать в `.env`:

```dotenv
DIRECTORY_FILE=G:/Project/wb-monitor-61373/data/directory.json
```

После первого импорта это значение повторно не применяется. Для обновления загрузите новый JSON через интерфейс. Рабочие данные и SQLite находятся в `data/portal.sqlite` рядом с проектом и сохраняются между перезапусками. Не заменяйте папку `data` при обновлении.

## Создание заявки

В разделе «Заявки логистов» нажмите «Создать заявку». Поля:

- Номер маршрута (числовой `route_id`).
- Дата подачи по Екатеринбургу, обязательная.
- Приоритет экипажа (1 — основной, 2 и далее — резервные).
- Водитель и автомобиль из импортированного справочника.
- Прицеп, необязательный.
- Комментарий, необязательный.

На один маршрут и дату можно создать несколько заявок с разными экипажами. Планирование резервирует водителя, автомобиль и прицеп **на весь выбранный день**. Повторное использование ресурса в другой активной заявке на ту же дату блокируется сервером с указанием номера конфликтующей заявки. Это консервативная проверка внутри портала; расписание по часам и занятость в WB пока не подключены.

Планы можно редактировать, приостанавливать, возобновлять и переносить в архив. Пауза и архив освобождают ресурсы. Возобновление повторно проверяет конфликт. Одновременное редактирование одной записи двумя логистами защищено версией: второй пользователь получит предложение обновить список. Приоритет сохраняется для будущей интеграции; сейчас он не запускает выбор экипажа в мониторинге.

Каждое действие записывается в «Историю изменений». Администратор добавляет логистов в разделе «Команда». Логисты видят общие планы и могут менять их; импорт справочников и добавление сотрудников доступны только администратору. Вход сохраняется на 24 часа. Нет восстановления/изменения пароля и управления отключением сотрудников в этой первой версии — используйте для ограниченной команды, эти функции можно добавить следующим этапом.

## Граница интеграции

**Создание заявки здесь не принимает транспортную заявку Wildberries.** После настройки и включения встроенный бот читает API WB по маршрутам и датам из планов, подтверждает кандидатов карточками и показывает их администратору. Принятие и назначение экипажей в WB не реализованы. Отдельный старый монитор с этой базой не связан.

## Сервер

На VPS с Docker создайте `.env` из шаблона и задайте длинный случайный SETUP_TOKEN. Например, сгенерировать его локально:

```sh
node -e "console.log(require('node:crypto').randomBytes(24).toString('hex'))"
```

Скопируйте результат только в `.env`, затем:

```sh
docker compose up -d --build
docker compose logs -f portal
```

Порт 8787 привязан только к loopback сервера. Для доступа с компьютера используйте SSH-туннель либо настройте свой HTTPS-прокси и домен. За собственным HTTPS-прокси установите `TRUST_PROXY=1`, проксируйте исходный `Host` и `X-Forwarded-Proto: https`. Не открывайте внутренний HTTP-порт наружу. Для SSH-туннеля `TRUST_PROXY=0`; зайдите на http://127.0.0.1:8787 и введите SETUP_TOKEN при первичной настройке. Cookie авторизации HttpOnly, SameSite=Lax, за настроенным HTTPS-прокси также Secure. Запросы изменения проверяют Origin, пароли хешируются scrypt, после 10 неудачных попыток вход ограничивается на 15 минут.

SQLite хранится в именованном томе `portal_data`. Для первой версии достаточно одного процесса/одной реплики портала. Перед резервным копированием тома остановите контейнер (чтобы учесть WAL), скопируйте том целиком и запустите его снова. Для нескольких реплик/большой нагрузки потребуется переход на серверную СУБД.

## Версия 0.4.0: мониторинг в портале

В настройках бота можно задать интервал от 3 до 86400 секунд (по умолчанию 60). Интервал — пауза после завершения проверки; запросы последовательны. Направления и даты берутся из запланированных заявок.

Администратор видит журнал запросов в настройках бота: начало, HTTP-статус, завершение, длительность, результат или ошибку. Последние 2000 записей хранятся в SQLite, последние 100 показаны на странице; журнал также выводится в консоль сервера.

Для новой подходящей карточки записывается curl_preview с текстом cURL для PowerShell 7. Экипаж выбирается по приоритету, при равенстве — по ID плана. WB_TOKEN — переменная окружения, настоящий токен не записывается. Запрос принятия никогда не отправляется. Для экипажа с прицепом команда не формируется, пока не подтверждено название поля прицепа в API. Повторные неизменившиеся карточки не создают повторных cURL.

Для запуска создайте планы, сохраните токен, задайте интервал и включите бота. При обновлении сохраните .env, базу данных и bot-secret.key. Ошибки 429 вызывают паузу с учётом Retry-After, 401/403 выключают монитор.

## Версия 0.10.0: реальное принятие

После обновления реальное принятие по умолчанию выключено. В настройках сохраните supplier_id своей компании, включите «Принимать заявки в WB» и сохраните настройки. Экипаж берётся из активного плана по приоритету, затем ID. Запрос содержит vehicle, driver, freelancerID:null, accept_round_trip:false. Планы с прицепом пропускаются до подтверждения поля API.

Начинайте с одного активного плана. Существующие планы не удаляются; после обновления без включения приёма остаётся прежний режим cURL. Успех подтверждается ID карточки, маршрутом, supplier_id, driver_id и vehicle_id. После успеха план и другие активные планы того же водителя/автомобиля ставятся на паузу; автор получает настоящее уведомление. Один уже исполненный план повторно не принимается: для нового рейса создайте новый план.

Попытка резервируется в SQLite перед PUT, в том числе между процессами. 409 повторяется не раньше чем через 60 секунд, максимум три попытки на карточку. 429 соблюдает Retry-After и откладывает опрос. 401/403 выключает бота. Неопределённый результат (обрыв, тайм-аут, неполный ответ, 5xx) блокирует повторный PUT и экипаж; на следующих циклах выполняется GET карточки. Если WB подтверждает назначение, завершается успехом; если назначен другой экипаж — ошибка. Если карточка всё ещё свободна, требуется ручная проверка — автоматического снятия неопределённой блокировки нет.

Полный ответ принятия хранится в acceptance_attempts, доступен администратору кнопкой «Ответ принятия» и через /api/bot/attempts/{WB_ID}. Токен из ответа удаляется. Исходный список TO_DELIVERY сохраняется как прежде. Проверки разработки используют только заглушки WB: реальные PUT при выпуске версии не выполнялись.

## Версия 0.13.2: статус после принятия и колонка результата

Страница заявок перечитывает данные каждые 5 секунд без перезагрузки и сохраняет выбранные фильтры. Во время ввода или редактирования формы автообновление откладывается. При открытии уведомления о принятии также запрашиваются актуальные планы.

Успешный план отображается как «В работе» с номером WB; появилась отдельная вкладка. В базе он остаётся приостановленным для мониторинга, а остальные активные планы того же экипажа ставятся на обычную паузу. Кнопка возобновления мониторинга у уже принятого плана скрыта. Архивирование доступно, запись результата сохраняется. Подтверждённый результат, уведомление и изменение состояния планов теперь записываются одной транзакцией — ошибка записи не оставляет ложный успешный результат без обновлённого плана.

Колонка результата принятия расширена, заголовок и пояснение расположены вертикально; название больше не сжимается до переноса по буквам. Таблица при недостатке места прокручивается внутри карточки.

## Версия 0.14.0: наблюдение за заявкой коллеги

У чужих активных планов есть кнопка «Следить» с колокольчиком. Повторное нажатие «Слежу» отключает подписку. Выбранные планы собраны во вкладке «Слежу» и в отдельном блоке обзора. Автор получает уведомления автоматически; подписка не меняет автора, экипаж, приоритет, статус или права пользователя.

При подтверждённом принятии бот сохраняет отдельное уведомление автору и каждому наблюдающему. В открытом портале у каждого появляется существующее окно со звуковым сигналом до нажатия «Ок». Подтверждение персональное: закрытие одним пользователем не подтверждает уведомления остальных. Подписки и непрочитанные уведомления сохраняются после перезапуска. После отключения подписки новые уведомления по этому плану не создаются; уже полученное уведомление требуется подтвердить отдельно. Нельзя подписаться задним числом на принятую или архивную заявку.

Проверены доставка нескольким получателям, отмена подписки, отсутствие дубликатов, независимое подтверждение, сохранение после перезапуска и привязка API к текущему пользователю. В браузере проверены «Следить» → «Слежу» и окно наблюдающего после имитации подтверждения WB без сетевых запросов к WB.

## Версия 0.14.1: понятные названия статусов

Вкладка «Запланировано» переименована в «На контроле» (активные планы), «В работе» — в «Обработано» (WB подтвердил принятие). Для строк и дашборда используются уточнения: «Мониторинг» при включённом боте и наступившей дате; «Ожидает даты» для будущих планов; «Ожидает запуска» при выключенном боте; «Обработана» для принятой заявки. Архив и ручная пауза сохраняют свои названия. Серый индикатор ожидания отличает его от мониторинга. Название обновляется при изменении состояния бота, даже если сам план не менялся. Внутренние статусы, заявки и история сохранены.

## Версия 0.14.2: локальное восстановление пароля

На компьютере сервера остановите портал и выполните из его папки:

```powershell
npm.cmd run administrator -- --list
npm.cmd run password-reset -- ЛОГИН
```

Команда использует DATABASE_FILE из .env и показывает выбранную базу и имя учётной записи до ввода. Новый пароль (10–200 символов) вводится дважды скрыто, без передачи аргументом командной строки. Права, планы и настройки сохраняются; старые сеансы только этой учётной записи отзываются. Затем запустите портал обычной командой. Старый пароль нельзя прочитать, поскольку в базе хранится хеш. Если база не найдена, новая пустая база не создаётся.

## Версия 0.14.3: компактное наблюдение

Колокольчик подписки вынесен в отдельную колонку «Следить». В кнопке нет текста; активная подписка выделена цветом, действие поясняется подсказкой и доступным названием. У статуса «Обработана» вместо зелёной точки показывается зелёная галочка. Мобильная карточка сохраняет подпись «Следить» рядом с колокольчиком, действия расположены отдельно.
